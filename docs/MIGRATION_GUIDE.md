# 기존 문서 이관 지침

> 신규 작성에서는 이 문서를 읽지 않는다. 기존 프로젝트 문서를 표준형 구조로 옮길 때만 사용한다.

## 목적

기존 문서를 몇 개의 요약 문단으로 바꾸는 작업이 아니다.

> 상세 이관: 기존 프로젝트를 계속 개발·운영하는 데 필요한 정보의 의미, 조건, 예외, 수치, 절차 및 판단 근거를 유지하면서 표준형의 책임 영역에 맞게 재구성하는 작업이다.

마이그레이션은 새 실험으로 검증 공백을 메우는 작업이 아니다. 이미 존재하는 절차, 당시 결과, 미완료 상태와 이후 변경에 따른 검증 공백을 사실대로 옮긴다.

| 구분 | 질문 |
|---|---|
| 문서 이관 상태 | 기존 지식·증거·공백이 새 문서에 빠짐없이 있는가 |
| 현재 검증 상태 | 현재 리비전에서 무엇이 통과·미실행·낡은 결과인가 |
| 릴리즈 준비 상태 | 현재 제품을 배포해도 되는가 |

세 상태를 섞지 않는다. 문서 이관 완료가 현재 제품의 모든 플랫폼 검증 통과를 뜻하지 않는다.

## 절차

```text
기존 문서 + 코드 + 테스트 + Git 이력 + 자산
        ↓
현황 조사
        ↓
정합성 확인
        ↓
표준 구조 배치
        ↓
상세 이관
        ↓
검증 근거 이관
        ↓
자산 이관
        ↓
누락 점검
        ↓
대체 가능성 점검
```

## 1. 현황 조사

기존 docs, 코드, 테스트, Git history, 있는 문서 자산과 기존 검증 기록을 목록화한다. 검증 기록은 날짜·리비전·출처가 있는지 함께 확인한다. 자산은 역할별로 적되, 없는 종류를 만들지 않는다.

## 2. 정본 판단

```text
현재 실행 코드 + 테스트
        ↓
승인된 ADR / 현재 계약 문서
        ↓
제품 / UI / 기술 명세
        ↓
진행 문서 / 계획
        ↓
과거 문서 / 메모 / Git history
```

Git은 근거 자료다. 기능 도입 시점, 과거 결정, 삭제된 기능, 문서-코드 분기 시점, 진행 상황 역구성에만 쓴다.

이 우선순위는 제품 사실을 판단하는 기준이다. 과거 테스트 결과의 유효 기간을 자동으로 연장하지 않는다. 검증 결과는 기록된 날짜와 리비전에만 직접 적용된다.

문서와 코드가 다르면 조용히 맞추지 않는다.

```text
문서가 오래된 것인가?
코드가 잘못 구현된 것인가?
의도적으로 변경된 것인가?
변경 결정 기록이 존재하는가?
```

확정 불가면 `DOC-CODE-MISMATCH` / `NEEDS-DECISION`. 필요하면 ADR.

## 3. 표준 구조 배치 = MAPPED

정보가 어느 문서로 가는지 정한다. 옛 파일 이름이 아니라 정보의 이동 위치를 README에 남긴다.

| 기존 정보 | 새로운 정본 |
|---|---|
| 제품 규칙 | 01_PRODUCT_SPEC |
| 화면 / 디자인 원칙 | 02_UI_UX |
| 코드 구조 / API | 03_TECH_SPEC |
| 배포 절차 | 04_DEVELOPMENT_WORKFLOW |
| 성능 조사 | PLAN-xxx |
| 중요 결정 | ADR-xxx |

이 단계만 끝난 상태를 REPLACEABLE로 착각하지 않는다.

## 4. 상세 이관 = MIGRATED

보존할 것:

```text
규칙 / 조건 / 예외
상태 전이
계산식 / 수치 / 표
API/데이터 계약
명령어 / 체크리스트
운영 절차 / 테스트 방법
장애 대응 / 성능 조사
플랫폼 제약
디자인 결정 및 근거
중요 프롬프트
문서용 이미지 / 다이어그램
날짜·리비전·출처가 붙은 기존 검증 결과
미완료 계획 / 미실행 검증 / 알려진 검증 공백
```

제거할 수 있는 것:

```text
중복
현재 의미 없는 임시 메모
폐기된 계획
깨진 링크
내용 없는 파일 목록
현재 사실과 맞지 않는 과거 설명
```

중요한 판단 근거는 ADR 또는 변경 기록으로 남긴다. 문장 복사가 아니라 의미와 세부 수준 유지가 기준이다.

진행 문서는 역사를 복원하지 않는다. Git과 현재 구현으로 완료 / 현재 / 막힘 / 다음 / 이후만 역기획한다.

## 5. 검증 근거 이관

검증 절차와 검증 결과를 구분해 옮긴다. 결과에는 아래 항목을 함께 기록한다.

| 항목 | 값 |
|---|---|
| 결과 | `PASS` / `FAIL` / `INCOMPLETE` / `NOT_RUN` / `UNKNOWN` |
| 근거 종류 | `HISTORICAL` / `RECHECKED` / `NONE` |
| 날짜 | 실행일. 모르면 `UNKNOWN` |
| 리비전 | 결과가 적용되는 커밋/태그/빌드. 모르면 `UNKNOWN` |
| 유효성 | `CURRENT` / `STALE` / `UNKNOWN` |
| 출처 | 원문, 로그, CI, Git 기록 |
| 공백 | 이후 변경 또는 아직 실행하지 않은 범위 |

규칙:
- 기존 결과를 옮기면 `HISTORICAL`이다. 이관 중 실제로 다시 실행한 결과만 `RECHECKED`다.
- 결과 뒤 관련 코드가 바뀌었다면 `STALE`로 표시한다. 과거 `PASS`를 현재 리비전의 `PASS`로 바꾸지 않는다.
- 원래 미완료인 Plan과 미실행 검증은 `INCOMPLETE` 또는 `NOT_RUN`으로 보존한다.
- 검증 공백 자체는 이관 실패가 아니다. 공백을 숨기거나 실행하지 않은 검증을 `PASS`로 쓰는 것이 실패다.

예:

| 검증 | 결과 | 근거 종류 | 날짜 | 리비전 | 유효성 | 공백 |
|---|---|---|---|---|---|---|
| NAS/AIT 재배포 | PASS | HISTORICAL | 08-15 | 당시 리비전 | STALE | 이후 오디오 변경 미재검증 |
| 테스트 133개 / 정적 분석 | PASS | RECHECKED | 08-23 | 이관 시 리비전 | CURRENT | 없음 |
| 장시간 실기기 카운터 | INCOMPLETE | HISTORICAL | UNKNOWN | PLAN-001 기준 | UNKNOWN | 원문부터 미완료 |

대체 가능성 점검 통과만을 위해 새 빌드, NAS/웹/실기기 스모크를 실행하지 않는다. 현재 리비전 재검증이 별도로 필요하면 이관과 분리된 작업/계획으로 승인받아 실행하고 새 결과로 기록한다.

## 6. 자산 이관

Markdown만 옮기면 대체할 수 없다. 이미지, 다이어그램, 제출 파일도 누락 점검 대상이다.

폴더 이름은 프로젝트마다 달라도 된다. 맞출 것은 경로가 아니라 역할이 섞이지 않는 것이다.

역할:
- 만든/검토한 디자인 후보
- 참고한 화면/자료
- 실제 구현 화면 (필요할 때만)
- 스토어/배포 제출 자산

규칙:
- 있는 자산만 옮긴다. 표준 구조를 맞추려고 빈 폴더를 만들지 않는다.
- 기존 프로젝트에 이미 쓰는 자산 폴더가 있으면 그 이름을 유지하고, README에 역할만 적는다.
- 없던 종류를 원본/표준 흉내 내려고 만들지 않는다. 실제 구현 스크린샷이 없으면 그 폴더를 만들지 않는다.
- 한 폴더에 참고 자료와 실제 구현 화면을 섞지 않는다.

아래 경로는 역할이 비어 새 폴더가 필요할 때의 예시일 뿐이다. 필수가 아니다.

    assets/design/
    assets/reference_images/
    assets/screenshots/
    assets/release/

## 7. 누락 점검

- 기존 기능 규칙이 모두 존재하는가?
- 예외 조건이 존재하는가?
- 계산식과 수치가 보존됐는가?
- API / 데이터 계약이 보존됐는가?
- 실행 / 빌드 / 배포 명령이 보존됐는가?
- 테스트 방법이 보존됐는가?
- 운영 절차가 보존됐는가?
- 디자인 원칙과 판단 근거가 보존됐는가?
- 이미지 / 다이어그램 / 참고 자료가 보존됐는가?
- 기존 검증 결과에 날짜·리비전·출처가 보존됐는가?
- 이후 변경으로 낡은 결과가 `STALE`로 표시되었는가?
- 원래 미완료·미실행·불명확한 검증이 그대로 드러나는가?
- 실행하지 않은 검증을 `PASS`로 기록하지 않았는가?
- 기존 문서를 열지 않아도 작업 가능한가?

자산 누락 점검: 원래 있던 자산만 검사한다. 없는 종류는 건너뛴다.

```text
[ ] 있던 디자인 후보/콘셉트 이미지가 보존되었는가? (없으면 N/A)
[ ] 있던 참고 이미지가 보존되었는가? (없으면 N/A)
[ ] 실제 구현 스크린샷이 필요했고 있었다면 보존되었는가? (없으면 N/A)
[ ] 있던 릴리즈/스토어 제출 자산이 보존되었는가? (없으면 N/A)
[ ] Markdown의 이미지 참조가 실제 파일을 가리키는가?
[ ] 자산 폴더 이름과 역할을 README에 적어 두었는가?
```

줄 수는 완전성 근거가 아니다.

```text
파일 존재
    ↓
제목 누락 점검
    ↓
규칙 / 표 / 계산식 누락 점검
    ↓
명령어 / 체크리스트 누락 점검
    ↓
자산 누락 점검
    ↓
Code ↔ Document consistency
    ↓
대체 가능성 점검
```

## 8. 대체 가능성 점검 = REPLACEABLE

기존 docs를 보지 않고 새 문서 팩만으로 아래를 올바르게 판단할 수 있어야 한다. 모든 검증을 지금 다시 통과시켜야 한다는 뜻이 아니다.

```text
[ ] 기존 docs 디렉터리를 보지 않고 프로젝트 목적을 설명할 수 있다.
[ ] 핵심 제품 규칙과 예외를 확인할 수 있다.
[ ] 주요 UI 흐름과 상태를 확인할 수 있다.
[ ] 아키텍처와 주요 코드 흐름을 이해할 수 있다.
[ ] API / 데이터 계약을 확인할 수 있다.
[ ] 테스트 / 빌드 / 배포 / 운영 절차와 명령을 확인할 수 있다.
[ ] 마지막 검증의 결과·날짜·리비전·출처를 확인할 수 있다.
[ ] 현재 유효한 결과와 `STALE` 결과를 구분할 수 있다.
[ ] 미실행·미완료·불명확한 검증 공백을 확인할 수 있다.
[ ] 주요 디자인 결정과 참고 자료를 확인할 수 있다.
[ ] 현재 상태와 알려진 문제를 알 수 있다.
[ ] 다음 작업자가 HANDOFF만으로 작업을 재개할 수 있다.
```

모두 충족해야 문서 팩이 REPLACEABLE이다. 이는 현재 런타임 검증이나 릴리즈 준비 상태가 모두 `PASS`라는 뜻이 아니다.

기존 docs의 삭제·Archive는 드러난 검증 공백과 복구 필요성을 사람이 검토한 뒤 결정한다. 공백을 닫기 위한 새 실험은 별도 작업이다.

## 9. 완료 단계

```text
MAPPED      정보가 어느 표준 문서로 갈지 정해짐
MIGRATED    세부 정보·자산·기존 검증 증거·검증 공백이 사실대로 이관됨
REPLACEABLE 기존 문서 없이 지식·증거·미완료 상태를 이해하고 작업을 재개할 수 있음
```
