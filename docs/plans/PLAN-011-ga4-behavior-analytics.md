# PLAN-011 GA4와 상세 행동 분석

## Metadata
- Plan ID: `PLAN-011`
- Status: `DRAFT`
- Related Requirement: 활성 사용자, 재방문, 유입, 퍼널과 게임 패턴
- Related ADR: ADR-009, PLAN-010에서 확정할 식별 결정
- Owner: 분석 연동 작업자와 독립 검수자
- Updated: 2026-09-29

## 1. 목표
기존 EventLogger를 통해 GA4에 필요한 행동을 전달하고, Supabase 판 요약과 연결해 해석 가능한 보고서를 만든다.

## 2. 범위
- 포함: 전송 어댑터, 이벤트/필드 사전, 채널과 환경 구분, 보고서와 수집 검증.
- 제외: 현재 실행의 SDK 설치/외부 프로젝트 생성, 모든 프레임/보석 입력 전수 전송, 이메일/닉네임/토스 원본키 전송.

## 3. 현재 상태 / 전제
- 외부 분석 SDK 없음. EventLogger가 Supabase 미설정이면 수집하지 않으므로 GA4 활성화 조건은 독립시켜야 한다.
- PLAN-009의 판 단위와 시간 정의, PLAN-010의 식별 계약을 먼저 확정한다. 모든 채널의 로그인 구현 완료까지 기다릴 필요는 없다.
- GA4 자동 세션과 내부 앱 실행 session_id는 같은 개념이 아니다. 예약명 session_start/ad_reward를 그대로 전달하지 않는다.

## 4. 구현 계획
### Step 1: 측정 사전
- [ ] 지표 정의: 활성 플레이 사용자, D1/D7 재방문, 모드별 완료율, 메뉴/첫 플레이 퍼널, 레벨 재시도와 아이템 활용.
- [ ] GA4 자동/추천/맞춤 이벤트 매핑과 파라미터 예산(이벤트당 25개), bool 변환 등 제공자별 타입 정의.
- [ ] round_id/event_id 같은 고유값을 일반 보고서용 맞춤 측정기준에 무분별하게 등록하지 않는다.
- [ ] 게임 코드 → 공통 이벤트 → Supabase/GA4 어댑터 경계. 한 전송 경로의 실패가 다른 전송이나 게임을 막지 않는다.

### Step 2: 한 채널의 최소 연결
- [ ] 테스트용 GA4/Firebase 프로젝트와 운영 환경 분리. 프로젝트 식별값과 채널 선택은 연결 전에 확인한다.
- [ ] 기존 Wasm 빌드 호환 확인 후 메뉴/게임 진입/판 종료부터 연결한다.
- [ ] 동의/수집 설정 적용, 개발/QA 제외, 사용자 변경 시 분석 ID 정리.
- [ ] DebugView에서 의도한 이벤트 1회, 파라미터와 자동 수집 중복 없음 확인.

### Step 3: 상세 행동과 보고서
- [ ] PLAN-009 판 요약에 대응하는 숙련도/전략/재시도/아이템 지표를 추가한다.
- [ ] 활성/대기 시간을 구분하고 가입/게스트/채널 구분을 붙인다.
- [ ] 리텐션, 퍼널, 레벨별 실패/재시도, 버전/실험별 비교 보고서 작성.
- [ ] 첫 방문과 재방문, 차단/오프라인 누락을 포함해 Supabase와 차이가 나는 이유를 문서화한다.

## 5. 병렬 작업과 변경 범위
- 계약 확정 뒤 GA4 어댑터와 보고서 설계는 독립 가능하다. 공통 로거는 한 명만 수정한다.
- PLAN-012는 공통 식별/동의 계약 이후 별도 단계로 착수 가능하지만 동시에 출시하지 않는다.
- 예상: lib/services 분석 어댑터, app/main 초기화, 채널 빌드 설정과 운영 대시보드.

## 6. 검증 계획
- Mock 기반 매핑/예약명/중복/수집 비활성/제공자 장애 회귀.
- flutter analyze, 관련 test, Wasm build, 실제 DebugView와 채널별 수집.
- 실제 검증 전 GA4 연동 완료로 표시하지 않는다.

## 7. 위험 / 미해결 사항
- 계정/동의/보존 설정, 콘솔 프로젝트 미정. GA4와 내부 데이터의 세션/유저 정의 차이.
- 매 입력 전송 부하를 피하고 필요한 상세 입력은 표본화한다.

## 8. 완료 조건
- 사전, 코드, 실제 수집과 보고서가 일치하고 개인정보처리 안내와 Spec/Status가 갱신된다.
