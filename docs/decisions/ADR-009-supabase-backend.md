# ADR-009 — 서버 저장소를 Supabase로 옮기고 익명 로그인과 REST 직접 호출로 연결한다

- Status: Accepted (코드와 스키마 준비 완료, 원격 프로젝트 적용 대기)
- Date: 2026-09-23

## Context
- 게임 내 랭킹은 NAS의 `matchranking/ranking.php`가 JSON 파일 두 개(모드별 상위 30건)에 저장했다. 인증이 없어 누구나 임의 점수를 제출할 수 있고, 30건 밖 기록은 남지 않는다.
- 아이템 보충 광고의 하루 3회 제한은 세션 메모리라 앱을 다시 켜면 풀린다(BR-103, ISSUE-003). 서버 영속(PLAN-002)은 사용자 식별 정책이 없어 막혀 있었다.
- 미출시라 외부 지표가 없고 분석 도구도 없다(ISSUE-006).
- 사용자가 2026-09-23 Supabase 조직을 지정하고 "설정과 저장이 필요한 부분을 Supabase로 세팅해 사용"하라고 요청했다. 기존 NAS 랭킹 기록은 유지할 필요가 없다고 결정했다.
- 웹 배포는 `--wasm` 빌드다. 앱인토스 WebView에서도 같은 웹 빌드가 돈다.

## Decision
1. 서버 저장소는 사용자 조직의 Supabase 프로젝트 하나로 한다. 스키마는 `supabase/migrations/`에 버전 관리한다.
2. 사용자 식별은 Supabase 익명 로그인이다. 설치 또는 브라우저 저장소 단위의 익명 사용자이며 토스 사용자 식별자, 이메일, 전화번호를 받지 않는다.
3. 클라이언트는 공식 `supabase_flutter` 대신 기존 `http` 패키지로 Auth와 PostgREST를 직접 호출한다(`lib/services/backend/supabase_gateway.dart`).
4. 연결 값은 공개용 키(publishable key)와 프로젝트 URL만 쓰고 `--dart-define-from-file=config/supabase.json`으로 넣는다. `config/supabase.json`은 Git에서 제외한다. secret 키와 service_role 키는 클라이언트, 저장소, 문서에 두지 않는다.
5. 저장 대상:
   - `ranking_entries`와 RPC `get_ranking`, `submit_ranking`: 게임 내 랭킹. 앱인토스 공식 리더보드(API-005)는 그대로 둔다.
   - `app_config`: 서버 함수가 읽는 원격 설정(랭킹 표시 개수, 보충 광고 하루 제한).
   - `ad_refill_claims`와 RPC `ad_refill_status`, `claim_ad_refill`: 보충 광고 하루 제한(KST 날짜, 익명 사용자 단위).
   - `game_events`: 내부 이벤트 로그. 클라이언트는 쓰기만 한다.
6. 랭킹 저장소를 Supabase로 옮기고 NAS 기록은 가져오지 않는다. NAS의 `ranking.php`는 새 빌드 배포 뒤 폐기 시점을 따로 정한다.
7. 서버 검증은 명백한 이상값(점수 상한, 이름 길이)과 과도한 요청(사용자당 분당 랭킹 10건, 이벤트 300건)을 막는 수준이다. 치트 방지가 아니다.
8. 장애 처리: 미설정 빌드나 서버 장애에서 랭킹은 기존 실패 메시지를 보이고, 보충 광고는 세션 로컬 제한으로 판단하며, 이벤트는 큐에 보관 후 재시도하거나 버린다. 어떤 경우에도 플레이와 나가기를 막지 않는다(BR-002).

## Alternatives Considered
- 대안 A: NAS PHP 유지와 DB 추가. 인증, 권한, 백업, 관측을 직접 만들어야 한다.
- 대안 B: `supabase_flutter` SDK. 세션 관리와 재시도는 편하지만 의존성이 크게 늘고, `--wasm` 빌드 호환을 따로 검증해야 한다. 필요한 호출은 익명 가입, 토큰 갱신, RPC, 삽입 네 가지뿐이다.
- 대안 C: Firebase(GA4, Firestore). 분석은 강하지만 사용자가 지정한 플랫폼이 아니고, 채널별 SDK와 동의 정책이 더 필요하다.
- 대안 D: 검증을 Edge Function에 둔다. 지금 규모에서는 DB 제약과 트리거로 충분하다.

## Reason
- 익명 로그인으로 PLAN-002의 식별 문제를 개인정보 없이 풀 수 있다.
- RLS와 열 단위 권한으로 사용자 ID를 공개하지 않고 랭킹을 공개할 수 있다.
- REST 직접 호출은 Wasm 빌드와 기존 테스트 방식(`http` + `MockClient`)을 그대로 쓴다. 2026-09-23 `--wasm` 릴리즈 빌드와 전체 테스트로 확인했다.
- 마이그레이션 파일로 스키마를 코드와 함께 리뷰할 수 있다.

## Consequences
- 장점: 랭킹 기록 영속과 제출자 식별, 보충 광고 제한의 재시작 우회 차단, 출시 후 지표 수집 경로 확보.
- 단점/비용:
  - 익명 사용자는 저장소 삭제, 재설치, 기기 변경 때 새 사용자가 된다. 보충 제한도 이 방법으로는 풀린다.
  - 무료 요금제 프로젝트는 일정 기간 요청이 없으면 일시 중지될 수 있다. 출시 전 요금제를 확인한다.
  - 익명 사용자와 이벤트 행이 계속 쌓인다. 보존 기간 정리 작업이 필요하다.
  - 개인정보처리방침과 스토어 데이터 안내에 익명 식별자, 이름, 점수, 이벤트 수집을 반영해야 한다.
- 후속 영향:
  - 운영 랭킹 초기화는 NAS 토큰 API 대신 Supabase SQL로 한다. 승인, 백업, dry-run(건수 조회), 예상 건수 고정, 사후 조회 순서는 유지한다.
  - PLAN-003(영속 인벤토리), PLAN-005(기록과 배지, 일일 보드)는 같은 프로젝트에 테이블을 추가하는 방식으로 이어 간다.
